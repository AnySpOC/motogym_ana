# GoPro MP4センサー比較レポート（2026-10-03）

## 1. 目的

3走行のGoProオリジナルMP4に埋め込まれたGPMFテレメトリを抽出し、iPhone CSVの前後G、横G、ヨーレートを独立センサーと比較した。GPXだけでは確認できない高周波振動、軸方向、時間遅延を評価し、モデル改善に使えるか判定する。

## 2. 取得できたデータ

|走行|動画時間|ACCL|GYRO|GPS9|CORI/GRAV|
|---|---:|---:|---:|---:|---:|
|Run 1 / GX010054|207.29 s|41,360点 / 199.53 Hz|41,360点 / 199.53 Hz|2,072点 / 10.00 Hz|12,425点 / 59.94 Hz|
|Run 2 / GX010057|557.52 s|111,243点 / 199.53 Hz|111,243点 / 199.53 Hz|5,575点 / 10.00 Hz|33,418点 / 59.94 Hz|
|Run 3 / GX010060|146.70 s|29,279点 / 199.59 Hz|29,279点 / 199.59 Hz|1,466点 / 10.00 Hz|8,793点 / 59.94 Hz|

GPS9の点数は外部GPXと一致した。外部GPXは埋め込みGPSと同じ系列と判断できる。再圧縮された`(1).MP4`には`gpmd`トラックがなく、センサー解析にはオリジナルMP4が必要である。

## 3. 比較方法

- CSVファイル名のUTC開始時刻とGPX先頭時刻から動画内時刻へ変換する。
- GoPro ACCLは200 ms窓、GYROは100 ms窓で平均し、エンジン振動とサンプル位相差を抑える。
- GoPro 3軸について軸、符号、-5.0から+5.0秒の時間差を探索する。
- ACCLは`m/s^2`からG、GYROは`rad/s`から`deg/s`へ変換する。
- 加速度RMSEは一定の取り付け・重力バイアスを除いた値も計算する。

## 4. 結果

|走行|前後G 相関 / RMSE|横G 相関 / RMSE|ヨー 相関 / RMSE|最良時間差|
|---|---:|---:|---:|---:|
|Run 1|0.86 / 0.06 G|0.34 / 0.06 G|0.48 / 3.48 deg/s|0.0から+0.2 s|
|Run 2|0.83 / 0.05 G|0.64 / 0.05 G|0.31 / 5.04 deg/s|-0.1から+0.2 s|
|Run 3|0.88 / 0.04 G|0.57 / 0.03 G|0.22 / 3.86 deg/s|-0.1から+0.1 s|

前後Gは全走行で高い相関となり、iPhoneの重力除去加速度と車体前後軸推定が概ね実運動を捉えている。Run 2ではGoPro軸の符号が他走行と逆で、取り付け方向の変更または動画姿勢メタデータの影響が確認された。比較器の符号探索により吸収できる。

横Gは前後Gより相関が低い。低速区間では横加速度自体が小さく、バンク、旋回、路面振動、両端末の取り付け位置差の影響が相対的に大きいためである。

ヨーレートは加速度ほど一致しない。今回のCSVは端末単軸に依存した旧方式の影響を含む。現行実装は3軸ジャイロをキャリブレーション時の車体鉛直方向へ射影するため、次回収録で同じ比較を再実行して改善量を確認する。

## 5. モデル改善への反映

1. 速度積分前の低域通過は必要である。生サンプル比較のRun 3前後G相関は0.223だったが、200 ms平均では0.878になった。
2. 端末・カメラの軸番号や符号を固定値として扱わない。キャリブレーションと3軸投影を維持する。
3. GoPro GYRO/CORI/GRAVを次回の3軸ジャイロ評価に使う。今回の値だけでヨー観測ノイズを変更しない。
4. 約0.1から0.2秒の遅延は自動START時刻へ影響し得る。次回は同一の発進イベントでiPhoneとGoProのピーク時刻を確認する。
5. Run 2のiPhone IMUには約231秒の欠測があるため、速度モデル改善の学習対象から欠測区間を除外する。

## 6. 再実行

```powershell
pnpm install
pnpm analyze:gopro -- --mp4 <original.MP4> --csv <gym-ana.csv> --gpx <video.gpx> --out <summary.json>
```

出力JSONには統計と比較結果だけを保存し、位置座標と全サンプルは含めない。

## 7. 前方映像による停止・走行判定

再圧縮版`(1).MP4`を160×90ピクセル、5 fpsのグレースケールへ縮小し、画面差分と疎なオプティカルフローを算出した。GPX速度1.5 km/h以下を停止、5 km/h以上を走行として、映像ごとにフロー閾値を探索した。

|走行|フローと速度の相関|最良閾値|停止／走行バランス精度|停止再現率|走行再現率|
|---|---:|---:|---:|---:|---:|
|Run 1|0.66|0.93 px|0.97|0.97|0.98|
|Run 2|0.43|0.43 px|0.97|0.98|0.97|
|Run 3|0.38|1.15 px|0.95|1.00|0.91|

映像フローは速度値そのものの推定より、停止中か走行中かの独立判定に有効である。閾値は画角、路面模様、明るさで変化するため、アプリの固定閾値には使わず、既存ログの状態判定を評価する正解ラベルとして使用する。

イベント照合では、Run 1とRun 2は手動開始、Run 3は自動発進検出だった。Run 2の手動開始時はGoPro GPSが約17 km/hであるのにアプリ速度は0 km/hで開始しており、走行中の手動開始にGPS初期速度を使う現行改善の妥当性を裏付ける。Run 2とRun 3の手動STOP時はそれぞれ約35 km/h、24 km/hで映像フローも走行を示すため、これらを自動停止判定の正解データとして扱ってはならない。

```powershell
pnpm analyze:video -- --mp4 <video (1).MP4> --gpx <video.gpx> --csv <gym-ana.csv> --out <motion.json>
```

出力には映像フレームとGPS座標を含めず、時刻ごとの派生モーション量と評価統計だけを保存する。
